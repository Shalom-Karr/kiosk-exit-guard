v1.1.10 — service spawn reliability + log-noise cleanup

The kiosk now actually survives a reboot on machines where v1.1.3–v1.1.9's gopsutil-based explorer-token fallback was returning empty. Field report: spawnControllerInSession(1) failed: WTSQueryUserToken(1): An attempt was made to reference a token that does not exist.; explorer fallback: no explorer.exe found in session 1 (is a user logged in?) firing every 2 seconds even though the user WAS logged in and running the kiosk. Root cause: gopsutil's process.Processes() can return a filtered or empty list when called from the Session-0 LocalSystem service — the kernel can see across sessions just fine for LocalSystem (it has SeDebugPrivilege), but gopsutil's underlying snapshot API was missing them. Fix: switched the cross-session enumeration to WTSEnumerateProcessesExW from wtsapi32.dll, the Win32 API explicitly designed for service-side cross-session enumeration. Pass the target sessionID directly so the kernel filters for us. Broadened the candidate process list beyond explorer.exe to include sihost.exe, taskhostw.exe, RuntimeBroker.exe, and StartMenuExperienceHost.exe — all Windows-auto-spawned under the interactive user's token, all serving the same purpose. Priority order preserved (explorer.exe first, others as fallback). The v1.1.8 QueryFullProcessImageName image-path validation against the canonical %SystemRoot% path is preserved per-candidate so an attacker can't drop a sihost.exe in a writable directory and have its token used. Plus two log-noise cleanups: tightenHKLMConfigDACL no longer logs SetNamedSecurityInfo … The system cannot find the file specified. on fresh installs (the HKLM key only exists after the first saveHashToRegistry; we now silently skip ERROR_FILE_NOT_FOUND and let the save tighten it); and parentProcessImagePath no longer logs OpenProcess(parent=…) failed: The parameter is incorrect. on the v1.1.8 relocate-and-reexec flow (the original parent has exited by the time the re-execed child runs the parent lookup; ERROR_INVALID_PARAMETER / ERROR_ACCESS_DENIED are now silently absorbed). See the changelog for per-finding root cause + fix.

v1.1.9 — UX pass

Eleven concrete UX fixes plus a new "password modal can't be left up forever" rule. Headline fixes: the password modal now auto-dismisses after 30s of inactivity so a user who walked away can't hold the kiosk hostage (the kgSubmit / kgCancel bindings reset the timer so an actively-typing user isn't yanked mid-attempt); the v1.1.4 co-installed Service/scheduled-task race at logon used to blink the kiosk WebView2 child as the loser's supervisor respawned — now gated by a new Global\KioskExitGuardControllerRunning Win32 mutex so the second mover exits cleanly without killing the first; controller panics now spawn a "SK Filter restarted after an internal error" toast before the process tears down so the user understands the brief glitch instead of seeing a black flash; first-run setup builds ONE combined status dialog from (svcErr, taskErr) with "Auto-start: Windows Service ✓, Scheduled task ✓" (or any combination of ✓/✗) instead of stacking a zenity.Warning + zenity.Error on dual-failure; the pause shortcut writes a pause-just-applied.flag marker under %ProgramData% before killing the kiosk so the controller's 30s watchdog can't relaunch the kiosk in the gap before the 2s sync loop sees the new pause file; --update now polls SCM until the service actually reaches svc.Stopped before renaming the exe (was returning from sc stop immediately, letting the supervisor respawn a fresh controller mid-rename); modal-spawn failures (AV quarantine, missing exe) now surface a "Password prompt failed. Check kiosk-exit-guard.log" toast instead of being silently swallowed; the three exit-after-failure call sites (--pause, --update, --set-url) now use a synchronous showFailedToastSync so os.Exit(1) doesn't kill the fire-and-forget child mid-paint; the uninstall dialog now mentions the Windows Service in the bulleted "this removes:" list and the post-uninstall verification block calls serviceStillExists() alongside the scheduled-task query; docs/admin-runbook.md updated for v1.1.4+ co-installed auto-start and v1.1.8 install paths. See the changelog for per-finding root cause + fix.

v1.1.8 — security audit pass

Nine findings from a full security audit, all closed. Headline fixes: the exe is now relocated to %ProgramFiles%\KioskExitGuard\ at first run so the SCM-registered binary path lives in an admin-only directory (a kiosk user can no longer swap the running binary and have the supervising Service respawn attacker code as LocalSystem); --update stages downloads in an icacls-locked %ProgramData% subdirectory and verifies SHA-256 against a new kiosk-exit-guard.exe.sha256 sidecar asset published alongside every release; the explorer.exe-token fallback (v1.1.3) now authenticates the candidate process by QueryFullProcessImageName against %SystemRoot%\explorer.exe before unwrapping the linked elevated token; all four in-process WebView2 instances share a single admin-only user-data folder under %ProgramData% so a kiosk user can't plant a service-worker script that intercepts the password modal's kgSubmit binding; the HKLM password-hash key has an explicit SetNamedSecurityInfo DACL granting only SYSTEM + Administrators so a local user can no longer read the bcrypt hash and crack it offline; the LL keyboard hook is installed earlier in main() so the gap between killing the leftover controller and installing the new hook can't leave the kiosk briefly unprotected; installStartupTask moved exe path + task name to env-var passing and base64-encoded the PowerShell script body to harden against any future injection vector; isLaunchedByService now authenticates the supervising parent via CreateToolhelp32Snapshot + parent-PID image-path lookup instead of trusting a forgeable env-var marker. See the changelog for per-finding root cause + fix.

v1.1.7 — pause duration picker fix

Pause-duration picker visible on the fullscreen kiosk. v1.1.6 fixed the password modal's foreground-grab; this covers the screen AFTER the password — the "1 / 5 / 10 / 20 / 30 / 45 / custom" picker. User: "after the password when I tried to set if it was 1 minute or 5 or other that I couldn't see it." Root cause: askPauseDuration uses zenity.List (native Win32 dialog, not HWND_TOPMOST) — renders behind the kiosk's fullscreen topmost WebView2. Fix: kill the kiosk WebView2 child immediately after password accept and BEFORE the duration picker, so zenity gets normal foreground. On cancel the watchdog respawns the kiosk (or promptAndPause calls launchWebViewChild proactively).

v1.1.6 — password modal focus

Password modal now actually comes to front + gets keyboard focus on the fullscreen kiosk. User report: "pressing Ctrl+Shift+Alt+K while on the kiosk full screen needs to move the modal to the front to pause the filter." Root cause: both the kiosk window and the modal child were HWND_TOPMOST; the modal's z-order beat the kiosk visually, but keyboard focus stayed with the kiosk because the modal never called SetForegroundWindow (and Windows would have rejected the call anyway — only the foreground process can grant foreground to another). Fix: forceForeground uses the AttachThreadInput idiom — temporarily merge the modal thread's input queue with the foreground thread's queue, call SetForegroundWindow (Windows now treats them as one process for foreground-grant), detach. Bypasses the eligibility rules without the v0.5.4 modal-hang risk that originally caused the v1.0.3 strip.

v1.1.5 — zoom shortcuts allowed

Browser zoom shortcuts allowed through. Ctrl+0 (zoom reset), Ctrl+- (zoom out), and Ctrl++ / Ctrl+= (zoom in) now pass through the LL hook to the kiosk WebView2 page instead of triggering the password modal. Numpad equivalents (Ctrl+Numpad0, Ctrl+Subtract, Ctrl+Add) too. All variants still require Ctrl-only — Win+0, Alt+-, etc. still hit the lockdown path. Joins the existing always-allowed list of F5 and Ctrl+R.

v1.1.4 — belt-and-suspenders auto-start

Belt-and-suspenders auto-start: Service AND scheduled task co-installed. Field report: "right now the filter only runs when I re-click the exe file from the downloads folder." Even after v1.1.3's explorer.exe-token fallback shipped, the auto-start was still flaky on the affected machine. v1.1.0 had aggressively switched to Service-only and deleted any leftover scheduled task on install — which made the kiosk completely unprotected after reboot whenever the Service spawn path failed.
  • Install both: firstRunWithWizard and every non-service-spawn launch now register the Windows Service AND the scheduled task. Whichever fires first wins; killRunningController() at controller startup keeps exactly one controller alive.
  • Service no longer wipes the task on install. v1.1.0–v1.1.3 deleted the scheduled task inside installService to prevent the two managers fighting; v1.1.4 trusts killRunningController to keep things sane.
  • Scheduled task is AtLogon-only: dropped the every-1-minute respawn watchdog that v1.0.x had. The Service is the in-session respawn supervisor now; the task is purely a logon-time "make sure it starts" fallback. Keeping the per-minute trigger alongside the Service caused kill/respawn churn (both fire, second to start killRunningController's the first, loser's supervisor respawns, repeat).
  • Loud failure surfacing: if both auto-start installs fail, surface a zenity.Error so the admin can't silently end up with a kiosk that doesn't survive reboot.

v1.1.3 — controller crash + service spawn fixes

Two field-reported bugs the v1.1.0–v1.1.2 line missed.
  • Controller crashed when the LL hook tried to open the password modal. Symptom: fresh install, press Win once, modal flickers, panic, kiosk bypassed. Same bug class as v1.1.1 / v1.1.2 — go-webview2 panics on a process's second NewWithOptions call (chromium.go:131). The controller's first WebView2 is firstRunWithWizard; the next one (askPasswordModal via the hook callback) panics. v1.1.2 fixed showTimedInfo but I missed this call site, which is the bigger one because the hook callback uses it on every Win/Ctrl/Alt press. Fix: askPasswordModal now spawns kiosk-exit-guard.exe --ask-password <title> <subtitle> as a child process and reads its exit code (0=OK, 1=Wrong, 2=Cancel). The child's WebView2 is always its first; the controller's WebView2 budget stays at 1 for the life of the process.
  • Service couldn't spawn its child controller — "the filter only runs when I re-click the exe." WTSQueryUserToken returned ERROR_NO_TOKEN every 2 seconds for the entire session on the affected machine. The supervisor never got a primary token for the console user, so CreateProcessAsUserW never ran. After a reboot the kiosk had zero protection until the admin manually launched the exe. Fix: spawnControllerInSession now falls back to stealing explorer.exe's primary token in the same session when WTSQueryUserToken fails. To handle UAC-on admin users (where explorer runs with the limited half of a split token), the fallback unwraps to the linked elevated token via GetTokenInformation(TokenLinkedToken) — the controller needs admin to write HKLM, set IFEO debugger keys, and restart Explorer.

v1.1.2 — pause-expiry crash fix

Win key fell through to Explorer after a pause auto-expired — root-caused and fixed. Users hit a "SK Filter is already active" message from the Resume shortcut while the Windows key wasn't actually being blocked. Root cause: showTimedInfo still rendered the toast in-process via go-webview2. The controller had already used WebView2 once during the first-run wizard, so when autoReenableFilterMode fired at pause expiry, its showTimedInfo("Pause ended.") call was the second NewWithOptions in the controller's process. go-webview2 panics on the second instance per process (chromium.go:131, same bug class as v1.1.1's --update fix). The panic ran on the time.AfterFunc timer goroutine with no recover — the entire controller crashed. The supervising Service respawned it within ~1 s, but in that window the LL keyboard hook was gone and Win / Ctrl / Alt combos leaked through to Explorer. The same path bit every flow that paired askPasswordModal with a follow-up showFailedToast on wrong password (--pause, --update, --uninstall, --set-url, --reset).
  • All toasts now spawn a --show-toast child process. showTimedInfo exec's kiosk-exit-guard.exe --show-toast <ms> <text> as fire-and-forget; the child's WebView2 is always its first; it exits when the toast dismisses. The caller process never instantiates a second WebView2 itself, so the panic class is structurally eliminated.
  • Cleanup of v1.1.1's per-call workaround. runUpdateInvocation's manual exec.Command(exe, "--show-toast", ...) from v1.1.1 is reverted to a plain showTimedInfo call now that the universal path does the same thing.

v1.1.0 — Windows Service supervisor

Windows Service supervisor + LL-hook thread-pinning fix. v1.1.0 replaces the v1.0.x Task-Scheduler watchdog with a real Windows Service running as LocalSystem. The kiosk user can no longer reach schtasks /Delete to neutralize the auto-restart — Service control requires admin rights they don't have. The supervisor itself has no UI (Session 0 isolation since Vista); it spawns the existing controller into the active console session via CreateProcessAsUserW and respawns it within seconds if killed.
  • New KioskExitGuardSvc service running as LocalSystem, StartType = Automatic. Finds the active console session via WTSGetActiveConsoleSessionId, gets the user token via WTSQueryUserToken, duplicates to a primary token, builds a per-user environment block, spawns the controller into winsta0\default. Waits for exit, respawns. On sc stop it terminates the controller so it can't outlive its supervisor.
  • Two-process model: same exe, flag selects role. --service-run (SCM-only), --service-install, --service-remove, or no args for the controller.
  • First-run guard: Service sets KIOSK_EXIT_GUARD_VIA_SERVICE=1 in the spawned controller's env. If the controller boots with no password configured, it checks for that marker and exits silently — prevents the Service from respawn-looping a stack of first-run wizards on a half-installed device.
  • LL-hook thread pinning (v1.0.7 fix folded in): runtime.LockOSThread() at the top of main(). The Win32 LL hook is bound to its install thread; without pinning, the Go runtime would migrate the main goroutine after the WebView2 message loop in firstRunWithWizard() and the hook would silently go dead. Symptom on first-run installs: keyboard combos fell through instead of opening the password modal.

v1.0.6 — what's in the box

Production-readiness fixes from a multi-agent security audit. v1.0.6 closes six concrete escape paths in the 1.0.x line — five new bypasses an attacker with code-execution on the kiosk user could have used, plus two TOCTOU races in the hook itself:
  • Random per-process re-injection nonce replaces the fixed 0xC0DE marker — another process can no longer call SendInput with a known ExtraInfo value to slip past the LL hook.
  • Taskbar hidden via NoTaskbar=1 while active, closing the Start-button left-click → click kiosk taskbar entry → close escape.
  • WebView2 hardening: context menus, dev tools, status bar, zoom, and NewWindowRequested all disabled / rejected.
  • Accessibility helpers IFEO-blocked: sethc, osk, narrator, utilman, magnify — closes Sticky-Keys-5x-Shift and the Ease-of-Access escape.
  • Atomic CAS on the in-flight prompt flag inside hookCallback — a rapid second blocked combo can no longer race past the first and re-inject the wrong keystroke after auth.
  • Modifier snapshot taken synchronously inside the hook — re-injection always uses the modifier state at press time, even if the user lets go before the WebView2 modal opens.

WTSEnumerateProcessesExW cross-session fallbackv1.1.10

v1.1.3's WTSQueryUserToken-NO_TOKEN fallback enumerated processes via gopsutil to find explorer.exe in the active console session. On affected machines the snapshot returned empty when called from Session 0 / LocalSystem, so the supervisor logged "no explorer.exe found in session 1 (is a user logged in?)" every 2s and the kiosk never got a controller after reboot. Switched to WTSEnumerateProcessesExW from wtsapi32.dll — the Win32 API explicitly designed for service-side cross-session enumeration. Buffer freed via WTSFreeMemoryExW every call. unsafe.Sizeof sanity check before slicing so a layout mismatch fails clean instead of dereferencing garbage.

Broadened user-session candidate listv1.1.10

The fallback no longer requires explorer.exe. Custom kiosk shells and v1.1.x's Explorer-restart-that-didn't-respawn paths used to leave session 1 with no explorer.exe at all. Now matches any of explorer.exe · sihost.exe · taskhostw.exe · RuntimeBroker.exe · StartMenuExperienceHost.exe — all Windows-auto-spawned under the interactive user's token. Priority order preserved (explorer.exe first if present). Each candidate validates against its canonical %SystemRoot% image path via QueryFullProcessImageName so an attacker can't drop a sihost.exe in a writable directory and have its token used.

30s password-modal auto-dismissv1.1.9

A user who pressed Ctrl+Shift+Alt+K, saw the modal, then walked away used to leave the fullscreen password screen up forever — kiosk WebView2 was dead, the next person at the device saw a frozen modal with no way to dismiss. askPasswordModalInProcess now arms time.AfterFunc(30*time.Second, ...) that calls w.Dispatch(func(){ w.Terminate() }). The child exits with pwCancel (no failed-password toast); the kgSubmit / kgCancel bindings reset the timer so an actively-typing user isn't yanked mid-attempt.

Controller mutex stops logon-time kiosk blinkv1.1.9

v1.1.4 co-installed both Service and AtLogon task; at logon both fire within ~1s and the loser was being killed by the winner's killRunningController. The loser's supervisor respawned it, oscillation continued, kiosk WebView2 blinked / reopened 1 – 2s after logon. New Global\KioskExitGuardControllerRunning named Win32 mutex acquired before killRunningController — second mover logs "controller mutex already held; exiting" and os.Exit(0)s cleanly. First controller keeps running, no respawn loop.

Panic recovery toastv1.1.9

Pre-v1.1.9 a panic in the controller logged silently to kiosk-exit-guard.log and the user saw the desktop briefly while the Service / scheduled task respawned the controller. recoverAndLog now spawns a fire-and-forget --show-toast 5000 "SK Filter restarted after an internal error. Auto-recovery in progress." child before returning, so the user understands the brief glitch instead of being confused by an unexplained kiosk flash.

Exe relocated to %ProgramFiles%v1.1.8

First-run now copies the exe to %ProgramFiles%\KioskExitGuard\ and re-execs from there before registering the Service binary path, scheduled task, or desktop shortcuts. Previously the SCM-registered path was wherever the admin double-clicked from (usually Downloads, kiosk-user-writable) — a kiosk user could swap the binary and have the supervising Service respawn attacker code as LocalSystem. Falls back to in-place install on copy failure.

--update SHA-256 verified + admin-only stagingv1.1.8

Downloaded exe is now staged under %ProgramData%\KioskExitGuard\staging\ (admin-only DACL via icacls /inheritance:r) instead of %TEMP%, AND the SHA-256 is verified against a kiosk-exit-guard.exe.sha256 sidecar asset published by the release workflow alongside every release. Mismatch aborts with a zenity.Error and a pointer at the issue tracker.

HKLM hash DACL admin-onlyv1.1.8

The default HKLM\Software ACL inherits BUILTIN\Users:KEY_READ — any local user could read HKLM\Software\KioskExitGuard\PasswordHash and run an offline bcrypt-dictionary attack. SetNamedSecurityInfo(SE_REGISTRY_KEY, SDDL=D:PAI(A;CI;KA;;;SY)(A;CI;KA;;;BA)) on every controller startup grants only SYSTEM + Administrators; protected (no inherit) so the BUILTIN\Users ACE doesn't leak in.

explorer.exe-token fallback authenticatedv1.1.8

The v1.1.3 explorer.exe-token fallback for WTSQueryUserToken-NO_TOKEN previously trusted any process named explorer.exe. Now calls QueryFullProcessImageName on the kernel handle we just opened — rejects any candidate whose image path isn't %SystemRoot%\explorer.exe. Closes the renamed-binary impersonation AND the PID-recycle race in one stroke.

WebView2 profile under %ProgramData%v1.1.8

All four webview2.NewWithOptions call sites (password modal, toast, first-run wizard, kiosk page) now share %ProgramData%\KioskExitGuard\WebView2\ with the same locked-down DACL. The default %LOCALAPPDATA% profile was user-writable — a poisoned service worker could have intercepted the password modal's kgSubmit host-object call before bcrypt comparison.

Zoom shortcuts allowedv1.1.5

Ctrl+0, Ctrl+-, Ctrl++ / Ctrl+= (plus numpad variants) now pass through to the kiosk WebView2 page so admins / kiosk visitors can adjust zoom without entering the password. Ctrl-only — modifier combos like Win+0 / Alt+- still hit the lockdown.

Service + scheduled task co-installedv1.1.4

Both auto-start mechanisms registered on install. Service is the in-session respawn supervisor (LocalSystem in Session 0, kiosk user can't disable). Scheduled task is the AtLogon fallback that fires even on installs where WTSQueryUserToken + the v1.1.3 explorer-token fallback both somehow fail. Closes the "filter only runs when I re-click the exe" failure mode.

Task watchdog dropped, AtLogon-onlyv1.1.4

v1.0.x's every-1-minute respawn watchdog removed from the scheduled task. The Service handles in-session respawn now; keeping both watchdogs alongside each other caused kill/respawn churn. Task is now a single AtLogon trigger — boot-time fallback only.

Password modal via child processv1.1.3

askPasswordModal now exec's kiosk-exit-guard.exe --ask-password <title> <subtitle> as a child and reads its exit code (0 / 1 / 2 = OK / Wrong / Cancel). The child's WebView2 is always its first instance, so the controller (which already used WebView2 for firstRunWithWizard) never crashes on the LL-hook-triggered password modal. Closes the "fresh install, press Win once, kiosk bypassed" failure path.

explorer.exe token fallbackv1.1.3

When WTSQueryUserToken returns ERROR_NO_TOKEN (observed in production on Win11 Home), the supervisor falls back to finding explorer.exe in the active console session via ProcessIdToSessionId, calling OpenProcessToken, and (if UAC is on) unwrapping the limited half of the split token to the elevated linked token via GetTokenInformation(TokenLinkedToken). Closes the "filter only runs when I re-click the exe" failure path.

Toasts via child processv1.1.2

showTimedInfo always spawns kiosk-exit-guard.exe --show-toast as a fire-and-forget child. The caller's process is never the one to instantiate a second WebView2, structurally eliminating the go-webview2 double-instance panic that crashed the controller every time a pause auto-expired (and dropped the LL keyboard hook for ~1 s while the Service respawned).

Symptom users hit: Resume shortcut said "SK Filter is already active" but the Win key wasn't blocked. Root cause: autoReenableFilterMode's "Pause ended." toast was the controller's second in-process WebView2, panic'd on the time.AfterFunc goroutine (no recover), killed the controller. All features

WebView2 kiosk window

The kiosk page lives in this exe, not a Chrome subprocess. Fullscreen, topmost, frameless, JS-locked to refuse navigation away from the kiosk URL.

Chrome uninstalled on first run

Reads Chrome's UninstallString from the registry and runs the official uninstaller with --force-uninstall. Clean removal, idempotent if Chrome isn't installed.

Edge launches blocked at the OS

Sets HKLM\…\Image File Execution Options\msedge.exe\Debugger to redirect launches to kiosk-exit-guard --silent-exit. Same for chrome.exe. Re-applied every launch.

UAC elevation

Embedded manifest. Every launch requests admin consent cleanly. The Task Scheduler entry uses HIGHEST run level so logon launches are silent.

HKLM password storage

Bcrypt hash in HKLM\Software\KioskExitGuard\PasswordHash. Admin-write only — a standard kiosk user can't bypass by deleting a file.

Filter mode hotkey

Ctrl+Shift+Alt+K → password → flips ON/OFF. State persists across reboots.

Pause duration prompt

Toggling OFF asks "5m / 15m / 30m / 1h / Indefinite". Anything but Indefinite auto-re-enables.

Registry policy lockdown

Filter mode ON: DisableTaskMgr=1 and NoRun=1 under HKCU. Cleared when flipped OFF or via --reset.

How it works

One binary; the first command-line argument selects the role. v1.1.0 introduces the Windows Service supervisor on top of the existing controller architecture.

--service-run — SCM only. Runs as LocalSystem in Session 0. Finds the active console session, gets the user token, spawns the controller into the user session, watches it, respawns on death. No UI.
Controller (no args) — spawned by the Service via CreateProcessAsUserW into the user session. Owns the LL keyboard hook, filter-mode state, registry lockdown, and supervises the WebView2 kiosk child.
--webview — spawned by the controller when filter mode flips ON. Renders the fullscreen WebView2 kiosk window. Dies when filter mode flips OFF.
--silent-exit — how IFEO-blocked launches reach us. Windows passes the target exe's path as an extra arg. We exit immediately so the Chrome/Edge/accessibility-helper launch fails invisibly.

Boot sequence (steady state)

Windows boot → SCM auto-starts KioskExitGuardSvc (Session 0, LocalSystem)
↓ user logs on
Service detects console session via WTSGetActiveConsoleSessionId + WTSQueryUserToken
↓ CreateProcessAsUserW
Controller (user session) applies lockdown, installs LL hook, runs message loop
↓ filter mode = ON
--webview kiosk window opens (fullscreen, topmost)

If the controller dies (crash, manual kill, etc.), the Service waits a beat then spawns a fresh one. The kiosk user can't stop the Service — SCM rejects non-admin commands.

Pressing a blocked combo (filter active)

user presses Win+R → LL hook captures combo → swallows event
↓
branded SK Filter password modal opens (autofocused input)
↓ correct password
SendInput re-injects Win+R → Run dialog opens for real

The re-injected events carry a marker in ExtraInfo so the LL hook recognizes them as our own and lets them through. Wrong password → keystroke stays swallowed, "Wrong password" toast appears.

Pausing the SK Filter

Two equivalent entry points. Both invoke the same password modal and duration picker.

option A · hotkey Ctrl+Shift+Alt+K (handled inline by the controller)
option B · desktop "Pause SK Filter.lnk" (spawns a fresh --pause process; UAC consent)
↓
SK Filter password modal (autofocused)
↓ correct password
duration picker (1 / 5 / 10 / 20 / 30 / 45 / Custom 1–100)
↓
WebView2 kiosk closed · Edge IFEO block lifted · HKCU lockdown removed
↓ timer fires (1–100 minutes later)
filter re-activates automatically — back to baseline

When the desktop button is used, a 2-second polling goroutine in the running controller picks up the state change from the pause file and mirrors it into the controller's in-memory flags — keystroke hook stops blocking within ~2 seconds.

If the user triggers a pause while one is already in flight, they get a read-only status toast with the remaining time. There is no "end pause early" path — every pause runs its course.

Chrome remains uninstalled in both states — it was removed during first-run setup and isn't reinstalled by the pause. Only Edge re-launches are re-enabled during a pause.

When the pause timer fires, the state flips back to Active automatically: Edge IFEO block is re-applied, the registry lockdown is reapplied, and the WebView2 kiosk relaunches. No user action required.

Setup

  1. Download the exe (button above) and place it in C:\Program Files\KioskExitGuard\.
  2. Double-click. Approve the UAC prompt.
  3. WebView2 Runtime auto-installs if missing (~30 seconds, silent).
  4. First-run wizard opens — enter password (twice), confirm or change the kiosk URL.
  5. Setup then uninstalls Chrome, blocks Chrome+Edge launches, drops a desktop shortcut, and registers the logon task.
  6. The SK Filter is ON immediately after setup. Press Ctrl+Shift+Alt+K to pause it when needed.
SmartScreen on first launch. The exe is unsigned. Click More info → Run anyway. LL keyboard hook + unsigned exe matches keylogger heuristics — the alert is doing its job, but the exe is fine.
Server 2022 / stripped images. WebView2 Runtime isn't pre-installed on Server SKUs. v0.5.x auto-detects and installs it before opening the wizard — no manual step needed.

v1.1.0 onwards: the controller is spawned by the Service into the active user session via CreateProcessAsUserW, not by the user directly. Manually running the bare exe on a configured system is allowed but uncommon — first-run setup registers the Service and starts it automatically. Verify the Service is up with Get-Service KioskExitGuardSvc or sc query KioskExitGuardSvc.

--reset requires the configured password. If lost entirely, an admin can wipe HKLM\Software\KioskExitGuard via regedit to fully reset.

What it doesn't block

  • Ctrl+Alt+Del and Win+L — Windows Secure Attention Sequence, below any user-mode hook.
  • Booting from USB / safe mode bypasses everything. Set a BIOS password.
  • Another admin with an elevated terminal can still kill the exe. The Task Manager disable + IFEO blocks raise the bar for a standard kiosk user.
  • Third-party browser installed by an admin would not be IFEO-blocked unless you add it.
